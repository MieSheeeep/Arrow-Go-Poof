## 2. 项目介绍

玩家每次点击一个箭头，程序检查它沿自身方向到棋盘边界之间的同行或同列位置。如果没有其他箭头，Board 立即把它标记为已清除，Game 创建飞出动画；如果存在其他箭头，Board 返回首个 blocker，Game 立即扣除一次失误机会，CollisionAnimation 负责撞击、变红和回退。

与普通“正方形棋盘里零散放几个箭头”不同，本项目的棋盘是**不规则像素区域**：`U/D/L/R` 是四种方向箭头，`.` 是已露出的像素位置，`None` 是图案外的背景。只有属于图案的像素格才放置箭头，因此整个谜题的外轮廓会自然呈现像素画的形状（如月亮 Hello Kitty 的轮廓），而不是一个完整方框。箭头清除后，原位置显示颜色网格中的拼豆颜色，玩家在解谜过程中一点点“揭开”整幅像素画。

项目包含 ENCHANTED APPLE、BEAD BALL、MOON KITTY 三个关卡。每个关卡由二维箭头网格和颜色网格表示，三关均根据提交者提供的 `.px` 拼豆工程图案制作：附魔金苹果和精灵球为 16×16 固定网格，月亮 Hello Kitty 在设计阶段等比例压缩为 18×17；三个方向布局都通过固定种子生成、验证后复制为常量，因此每次启动布局相同，不会因随机生成而出现不可解关卡。

主要模块如下：

- `src/board.py`：纯规则层，负责网格校验、路径检测、点击结果和清除，不依赖 Pygame；
- `src/game.py`：负责生命值、失误次数、倒计时、开始/通关/失败/暂停状态、关卡索引和星级结算，并把规则结果转成动画；
- `src/animation.py`：不依赖 Pygame 的飞出、碰撞、扣心和星星弹出时间模型；
- `src/ui.py`：负责背景、棋盘、HUD（关卡/倒计时/生命/暂停）、开始/结果/暂停面板和坐标映射；
- `src/level_generator.py`：仅用于开发与测试；根据颜色掩码生成可解方向布局及其验证顺序，运行时不调用；
- `main.py`：负责 Pygame 初始化、事件分发、更新和绘制。

## 3. 实现思路

整体按 **Board / Game / UI 三层**划分。Board 只负责规则与棋盘状态，Game 负责流程状态并把一次点击转成动画，UI 只负责渲染和坐标换算。这样规则、状态和显示相互独立，动画的纯时间模型可以脱离 Pygame 单独测试。

路径检测从点击位置沿方向增量遍历：向上使用 `(-1, 0)`，向下使用 `(1, 0)`，向左使用 `(0, -1)`，向右使用 `(0, 1)`。遇到第一个箭头就返回 `blocked` 和 blocker 坐标；越过棋盘边界仍未找到箭头则返回 `clear`。

逻辑判定和动画分离。点击成功时 Board 立即清除箭头，因此动画期间仍可以点击其他合法箭头；碰撞动画期间原箭头仍在 Board 中，只有动画结束时才把起点加入 `error_cells`，保证“撞击后变红，回退后保持红色”的时间顺序。

扣心与动画同样分离：被阻挡时 `Game` 立即 `lives -= 1` 并记录失误，同时追加一个 `HeartLossAnimation`，让刚失去的那颗心在 HUD 上先放大闪烁再淡出，静态生命图标则随 `lives` 立即减少。

倒计时由 `Game` 的 `elapsed_seconds` 统一维护，只在 `PLAYING` 状态累加；进入开始页、通关页或失败页后自动冻结，暂停时同样停止，重开、下一关和返回菜单都会清零。HUD 显示的是 `remaining_seconds`（剩余时间），并用一条进度条配合颜色从平静过渡到紧急——剩余 25 秒内变黄、10 秒内变红并脉冲。星级改为与本关总得分挂钩：设初始箭头数为 `N`，理论最高分为 `5 × N × (N + 1)`；最终得分达到最高分的 85% 为 3 星，达到 60% 为 2 星，其余通关为 1 星。倒计时仍会导致超时失败，阻挡仍会打断 Combo 间接影响得分，但二者不再直接决定星级。评分作为不可变通关结果保存，因此不会随着结果页面停留时间继续变化；通关时由 `StarRevealAnimation` 让已获得的星星从空星位置逐颗弹出。

关卡的设计采用“先确定图案、再冻结布局”的方式：先用附魔金苹果、精灵球或 Hello Kitty 的颜色掩码确定可见轮廓；生成工具在仍存在的箭头中选择一条无阻挡射线，把该坐标加入清除顺序并记录方向。重复到所有格子被选中后，得到的顺序天然可通关。工具使用固定种子保证可复现，最终的箭头网格和通关顺序都写入 `levels.py` 常量，避免把随机性带进游戏运行时。

## 7. 心得体会草稿

这次作业让我第一次完整地走了一遍“用 AIGC 协作做一个小游戏”的流程，最大的体会是：AIGC 明显提高了需求拆分、代码骨架、测试用例和 Bug 定位的速度，但生成结果不能直接当作最终答案，每一步都需要本人验证。

印象最深的是飞出动画的 Bug。最初版本里箭头只移动固定的两格，逻辑上“有动画”，视觉上却根本没有飞出屏幕。这个问题单看代码和测试都很难察觉，是实际运行试玩后才发现的。于是我先补了一个失败的回归测试，再重新追踪 Board 清除、Game 动画列表和 UI 绘制之间的数据流，最终把飞出距离改为越过窗口边界的值。这件事让我理解了“测试只能覆盖你想得到的错误，真正的问题往往要靠运行和试玩才能暴露”。

分层设计也帮了很大忙。把 Board 的规则、Game 的状态和 UI 的渲染拆开后，动画的时间模型可以脱离 Pygame 单独测试，倒计时、扣心、按总分结算星级这些逻辑也都能用纯 Python 的单元测试覆盖，最终跑出 186 个通过的用例。没有这层边界，很多逻辑会散落在绘制代码里，既难改也难测。

总的来说，AI 更适合做协作型开发工具：它可以快速给出候选结构，但边界条件、交互体验、关卡可玩性和最终责任仍然需要本人通过测试和试玩确认。这次经历也让我对“先写测试、再改实现”的回归流程有了更具体的感受。
